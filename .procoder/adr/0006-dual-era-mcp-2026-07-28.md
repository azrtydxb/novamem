# 0006 — Serve MCP 2026-07-28 alongside the legacy handshake

Status: accepted
Date: 2026-09-10

## Context

An audit on 2026-09-10 found the server one full revision behind: it
advertised `2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25` while the
current revision is `2026-07-28`. That revision is the largest breaking
change MCP has had. It removes the `initialize` handshake,
protocol-level sessions and the `Mcp-Session-Id` header, the standalone
GET stream, `Last-Event-ID` resumability, and `ping`. Every request now
declares its own protocol version, client identity and capabilities in
`params._meta`, mirrors selected body fields into HTTP headers, and is
served on its own. `server/discover` becomes a MUST and replaces the
handshake as the way a client learns what a server speaks.

The spec names the two shapes: **legacy** (handshake, `2025-11-25` and
earlier) and **modern** (`2026-07-28` and later). Measured state before
this change:

- Dual-era clients worked against us, as the spec's compatibility matrix
  predicts; Claude Code connected and called tools.
- A modern-only client could not use the server at all.
- One confirmed MUST violation _within what we advertised_: `2025-03-26`
  requires implementations to receive JSON-RPC batches, and an array
  body was answered `-32700 Parse error`. Batching was removed again in
  `2025-06-18` and `2024-11-05` never required it, so the violation was
  scoped to that single advertised revision.

## Decision

Be **dual-era**: serve both shapes on the same `/mcp` endpoint, choosing
per request, exactly as the spec permits.

Era selection follows the spec's rules — an `initialize` selects legacy;
per-request modern `_meta` (or a modern `MCP-Protocol-Version` header,
or `server/discover`, which exists only in the modern era) selects
modern. The legacy path is untouched; the modern path never touches the
session registries.

The modern surface implements `server/discover`, `tools/list` and
`tools/call` with `resultType`, `ttlMs`/`cacheScope` cache hints and
`_meta` `serverInfo`; validates the required `MCP-Protocol-Version`,
`Mcp-Method` and `Mcp-Name` headers against the body (including the
`=?base64?…?=` sentinel decoding) and rejects disagreement with
`-32020 HeaderMismatch`; answers an unimplemented method with `404` and
`-32601`; and answers an unsupported version with `-32022
UnsupportedProtocolVersionError` carrying the list to retry from.

`2025-03-26` is dropped from the advertised list rather than fixing
batching for a dead-end code path. Advertising a revision is a promise,
and it was the only one requiring batch receipt. Clients predating the
`MCP-Protocol-Version` header are unaffected: they send no header, and a
headerless request is still served by the legacy path.

An `initialize` that asks for a version we do not speak now falls back
to the latest _legacy_ version rather than the latest overall. Handing a
legacy client `2026-07-28` would name a revision with no handshake for
it to finish.

`-32022` replaces the old `-32000` for an unsupported version header on
both eras. The code is load-bearing, not cosmetic: a dual-era client
treats a recognized modern error as "this server is modern, retry with
one of its versions" and anything else as "fall back to the handshake",
so returning the specified code is what stops a modern client from
needlessly downgrading. `-32000` remains correct for the other guard
bodies — the new error-code policy keeps `-32000`–`-32019`
implementation-defined and reserves `-32020`–`-32099` for the spec.

Rejected: **modern-only** (breaks every client that has not moved,
Claude Code included); **staying legacy** (correct, but no modern-only
client could ever use novamem); **doing nothing** (leaves the batching
violation standing).

## Consequences

- Modern-only clients can now use the server; legacy clients keep
  working unchanged, verified by a test that drives both eras through
  one endpoint and asserts neither disturbs the other.
- ADR 0005's signed, adoptable session ids stay in force for the legacy
  era and become irrelevant for modern traffic, which has no sessions at
  all. The direction of travel matches: sessions are going away.
- Not implemented, and deliberately so: `subscriptions/listen` (we emit
  no change notifications — `listChanged` is `false` and the tool list
  is frozen at compile time), MRTR/`InputRequiredResult` (no tool needs
  client input mid-call), and `x-mcp-header` (a client obligation; no
  tool parameter is annotated). Each becomes required only if the
  corresponding feature is added.
- Our `/mcp/sse` + `/mcp/messages` pair is the `2024-11-05` HTTP+SSE
  transport, now formally Deprecated with removal eligibility three
  months after SEP-2596 is Final. It is unchanged here and remains
  pod-local; retiring it is separate work.
- Roots, Sampling and Logging are Deprecated as of this revision
  (earliest removal 2027-07-28). We implement none of them, so there is
  nothing to migrate.
